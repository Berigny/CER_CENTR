# Design decisions

Short records of choices that are easy to revisit by accident. Newest last.

## D1. A neutral name

"CER" already means three things: Clinical Evaluation Report, the Clean Energy Regulator, and Consumer Energy Resources. The core is called `evidence/0`, with no domain or agency in the name. Domain work goes in profiles such as `centr/0`.

## D2. Point at the existing schema; don't restate the domain

The object carries `schema.ref` and `schema.hash` for whatever definition the system of record already has (DDL, JSON Schema, data dictionary). It does not copy domain enums or tables.

An earlier draft re-declared the CENTR domain (subject kinds, standards, roles, jurisdictions) in both the schema and a prime dictionary. The two drifted apart within one draft. Pointing at the source avoids that class of bug, and it means adoption needs no schema change in the system of record.

## D3. Beside the system of record, never instead of it

Evidence objects are written from changes and decisions in existing systems (for example from change-data-capture or an outbox table). They never write back. Turning the evidence layer off loses no operational data.

## D4. Signatures outside the object

Attestations are separate lines keyed by the object id, so approvals and witnesses can be added later without changing the id. This is carried over from the original evidence-object design.

## D5. Stricter than RFC 8785 on input

RFC 8785 says how to serialise; it assumes I-JSON input. evidence/0 enforces that: duplicate members, lone surrogates and numbers above 2^53 − 1 are errors.

The number rule is by magnitude, not by how the number is written. A rule like "integer literals must be ≤ 2^53 − 1" would reject the canonical form of some large floats (RFC 8785 writes 2^68 as `295147905179352830000`), so canonical output could fail to parse again. Bounding magnitude keeps parse(canonical(x)) always valid.

## D6. One small core, many profiles

The core has no gate clauses, prime coordinates, verdicts or registers. Those were in the earlier CENTR draft and are where most of its bugs were. They can come back as profiles and query layers once there is a concrete use, each with its own vectors.

## D7. The vectors are the contract

`test-vectors/` defines conformance. They are generated by an independent JavaScript implementation and checked by the Rust core, and CI fails if the two disagree or if the committed vectors differ from a fresh run.

This caught a real bug during the scaffold: Rust's shortest float formatting rounds exact ties up, while ECMAScript (and so RFC 8785) picks the even digit. 252 of the 4,024 number vectors failed until the tie-break was added.

## D8. Rust for the core

The core is the one part that must give byte-identical answers everywhere: canonicalisation, hashing, signature checks. One Rust implementation can ship as a command-line tool, a WebAssembly module (browser, Node, .NET or Java hosts) and Python or C bindings. Users on other stacks run the binary or module; they do not have to maintain Rust.

The WebAssembly module uses a one-function JSON ABI (`evidence_alloc`, `evidence_call`, `evidence_free`) rather than generated JavaScript glue, so the same file works in browsers, Node and non-JavaScript hosts. Python uses a native PyO3 extension instead of the WebAssembly module: it is the usual way to ship Python packages, and one abi3 wheel covers every CPython from 3.10.

## D9. Hand-written shape checks in the core

The core checks the schema rules in code rather than with a JSON Schema engine, to keep its dependencies to SHA-256, Ed25519 and base64. `tools/check_schema_vectors.py` runs the published JSON Schema over the same vectors in CI, so the two cannot drift silently.

## D10. Bytes in, not text

Every binding accepts file contents as bytes. If a binding took only text, a host's UTF-8 decoder would replace invalid bytes before the core saw them, and an object the command-line tool rejects with `E_PARSE` could verify in another language.

## D11. Observe before writing

Confirmed 26 November 2026, with the other roadmap decisions ([roadmap](roadmap.md#decisions-confirmed-26-november-2026)).

The evidence layer starts by only reading. It records what it observes in a system of record, and what people and services assert, using read-only access and no change to the system of record.

- Record changes in the log (`create`, `update`, `delete`) are only ever observations of a system of record. Anything the layer or an application states itself (a request, a decision, a check, a first sighting of an existing row) is an `assert`.
- Applications may later request changes through the layer, but only as explicit requests checked against an allow-list the system-of-record owner publishes, delivered through the system of record's own interface, off by default, and enabled per record type with the owner's agreement.
- While the layer only reads, D3 holds exactly. Once requests flow through it, turning it off still loses no confirmed change, but requests not yet delivered exist only in the layer, so applications then depend on it being available.

## D12. One SQLite file is the authoritative store

- Entries, objects, attestations and the projections that must agree with them (heads now; capture cursors and change keys from M2) are written in one transaction.
- Triggers refuse UPDATE and DELETE on the log tables.
- Query indexes (from M4) live in separate files that can be deleted and rebuilt.
- The portable form is an export of canonical JSON Lines segments with a manifest. It defines conformance: another backend conforms if its exports verify and match.
- Git or object storage receive exports as off-machine copies. Neither is ever the primary store.

## D13. Two clocks

- `at` stays the writer's claim and stays inside the id.
- The store adds its own facts outside the object, in the log entry: a dense position (`seq`) and `received_at`, which never decreases.
- Questions about what the store knew on a date use the store's clock. Questions about what was true at a time, according to the writers, use `at`.
- An `at` more than 5 minutes after `received_at` is counted in store reports, never rejected or rewritten.
- Objects that the store or its services author in a chain take `at` = the later of their clock and their predecessors' `at`, so a clock step backwards cannot break the prev ordering rule.
